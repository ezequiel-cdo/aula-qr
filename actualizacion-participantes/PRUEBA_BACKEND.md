# PAIVD 0.1 — ensayo restringido
No desplegar a público ni usar registros reales. No modificar V3. Dos proyectos independientes, ejecutados por el mismo responsable durante el ensayo. El almacén auxiliar Credenciales no duplica el maestro; contiene solo referencias a matrícula, hash, vigencia y estado. Su acceso se limita al propietario de ambos proyectos.
## Preparación
1. En un proyecto Apps Script privado nuevo, llamado EPJA_PAIVD_Administracion, copiar admin/PAIVD_DatosFicticios.gs y ejecutar PAIVD_CrearDatosFicticios una vez. Se crean dos libros nuevos, sin modificar el maestro, con dos homónimos ficticios. Anotar localmente los IDs de ambos libros y de las matrículas ficticias.
2. Copiar admin/PAIVD_Admin.gs y backend/PAIVD_Registro.gs al mismo proyecto privado, sin publicar. Crear propiedades PAIVD_TARGET_ID (ID libro ficticio), PAIVD_CREDENCIALES_ID (ID auxiliar ficticio), PAIVD_ENSAYO=SI, PAIVD_ADMIN_EMAIL (correo exacto del propietario) y PAIVD_SECRETO (64 caracteres hexadecimales aleatorios, generados localmente con generador criptográfico; no reutilizar ni compartir). Ejecutar PAIVD_PrepararCredenciales.
3. Crear otro proyecto Apps Script independiente EPJA_PAIVD_Participantes. Copiar backend/PAIVD_Registro.gs, backend/PAIVD_Participantes.gs y backend/FormularioPAIVD.html (HTML llamado FormularioPAIVD). Configurar las mismas cuatro propiedades compartidas, sin PAIVD_ADMIN_EMAIL. Nunca copiar admin, instalador o generador al proyecto participantes.
4. En el proyecto privado, configurar PAIVD_MATRICULA_EMISION con matrícula ficticia 1 y PAIVD_IDENTIDAD_COMPROBADA=SI (simulación de constatación). Ejecutar PAIVD_EmitirCredencial. El registro privado muestra código de un solo uso; no copiar a chat ni GitHub. Validez 48 h; sesión 30 min; selección 10 min. En producción hará falta entrega sin registro de texto plano, revocación, límites y gestión de recuperación robustos.
5. En proyecto participantes, Implementar > Probar implementaciones (URL /dev, solo editores autorizados). No desplegar /exec público. Seleccionar sección A, buscar Ensayo, escoger una coincidencia, introducir código. Si se elige el homónimo equivocado, el código debe fallar. Enviar formulario ficticio. Usar teléfonos de prueba 8095550101 y 8295550102, sin enviar mensajes ni efectuar llamadas.
## Criterios de aceptación pendientes
- Devuelve dos homónimos y hasta cinco coincidencias, nunca IDs internos.
- Credencial de persona A no funciona con selección B; incorrecta/vencida/reutilizada no concede sesión; no exceder cinco intentos por matrícula en 15 min. El límite global puede bloquear usuarios legítimos y no es defensa suficiente contra abuso público.
- Solo sesión válida permite enviar; no aceptar IDs del cliente. Verificacion_Identidad registra comprobación de credencial, Actualizaciones recibe una fila PENDIENTE con JSON; no escribe Contactos ni aprueba nada. Probar reenvío, teléfono compartido, ausencia de teléfono propio, datos inválidos, corrección y duplicados.
- Probar en móvil y verificar que no se guardan datos en sessionStorage ni se exponen por respuestas no autorizadas.
## Límites
Código de ensayo, no probado aún en Apps Script. No fotografía, fecha de nacimiento, verificación telefónica ni aprobación. No constituye autenticación de Aula QR. Los bloqueos de Apps Script no se comparten entre proyectos: no emitir simultáneamente con consumo durante ensayo. No hay transacciones entre libros ni revocación inmediata de sesiones; errores después de consumir código requieren nueva emisión. CacheService puede expulsar sesiones. Las credenciales se generan con Utilities.getUuid; revisar garantía criptográfica antes de producción. El secreto compartido debe custodiarse y rotarse. El nombre del libro no es prueba de entorno; comprobar IDs. La app pública requiere revisión de privacidad y seguridad, control de enumeración, cuotas, permisos y retención antes de cualquier despliegue. No usar datos reales en esta fase.
